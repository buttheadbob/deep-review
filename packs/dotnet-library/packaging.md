# Packaging, target frameworks and source generators

Passes P4, P10, P14 and P15, after the core files.

<a id="target-frameworks"></a>
## Target frameworks (P4)

- **Reach versus features:** `netstandard2.0` reaches net48 consumers but lacks newer APIs ([core runtime-differences](../../checks/core/runtime-differences.md#apis-that-dont-exist-on-net48)); `net8.0`/`net10.0` targets get the modern ones. Each target is its own build: `#if` branches per target get their own tests.
- **Polyfills:** a type the library adds for an older target (`IsExternalInit`, nullable attributes) is `internal`, so it doesn't clash with the consumer's own copy.
- **Trimming and AOT:** a library meant for AOT consumers (SimpleORMDotNet) sets `IsAotCompatible` (or `IsTrimmable`) so the trim and AOT analyzers run, and has no IL2xxx or IL3xxx warnings. Reflection, `Type.GetType` from strings and runtime code generation either go, or carry the right attributes so the consumer's build warns.

<a id="razor-class-libraries"></a>
## Razor class libraries (P4, P14)

- **A raw DLL reference is not a project reference.** A Razor class library consumed through `<Reference HintPath="...dll">` does not import its static web assets, scoped CSS or implicit framework references. If the library has `wwwroot`, `.razor.css` or a component that depends on a framework reference, the consumer needs a project/package reference or an explicit asset import. Document the constraint if a hub passes only the DLL.
- **Pack the component assets.** Read the `.nupkg` or the published folder: the component DLL and XML docs are not enough when the component ships `wwwroot` files, scoped CSS, or a `.deps.json`/framework reference.
- **Test the consumer shape.** Build a fresh consumer that references the library the way the product passes it (raw DLL, project reference, or package), then render the component. A build that only packs the DLL can pass while the consumer shows an unstyled control.

<a id="supply-chain"></a>
## Supply chain (P10)

- **What the package contains:** read the packed `.nupkg` file list. No test files, local configs, secrets, or build artifacts from other projects; the README and licence are in it.
- **Dependencies:** as few as the project promises ([api-design.md](api-design.md#dependencies)); each one restored from nuget.org with a pinned version; vulnerable ones get a verdict ([core security](../../checks/core/security.md#supply-chain)).
- **Build scripts and generators** in the repository run on every consumer's machine when they ship as analyzers or MSBuild targets in the package. Read them like code that runs with the consumer's rights.

## Package metadata (P14)

- **Identity:** `PackageId`, `Version`, `PackageLicenseExpression` (or a licence file), `RepositoryUrl`, `PackageReadmeFile`, a description that says what it does and what it needs. No template placeholders ([core docs-release](../../checks/core/docs-release.md#release-metadata)).
- **Reproducible and debuggable:** deterministic builds, `ContinuousIntegrationBuild` in CI, SourceLink, and symbols (`.snupkg`), so consumers can step into the code at the released commit.
- **XML documentation:** `GenerateDocumentationFile` on, and every public member documented: what it does, its exceptions, its thread safety. Missing docs on new public members are findings in a library.
- **Organization:** SimpleDiscordDotNet and SimpleORMDotNet are owned by the Simple-DotNet organization; their metadata names it, not a person.

## Source generators

- **Incremental only:** `IIncrementalGenerator`, never the old `ISourceGenerator`.
- **Cacheable pipelines:** the models flowing between steps are value-equatable records or structs, with no `ISymbol`, `SyntaxNode`, `Compilation` or `Location` inside. Otherwise every keystroke re-runs the generator in the consumer's IDE and holds whole compilations in memory.
- **Pure:** no file or network I/O, no clocks, no environment variables, no randomness. The same input gives the same output.
- **Generated code:** marked `// <auto-generated/>`, with `#nullable enable`, fully qualified `global::` type names, and no reliance on the consumer's usings or language version beyond what the generator checks.
- **Diagnostics:** stable ids, clear messages, a location in the consumer's code; reported instead of throwing. A generator exception shows up as a cryptic CS8785 warning and no output.
- **Packaging:** the generator targets `netstandard2.0`, ships under `analyzers/dotnet/cs`, and isn't referenced as a normal library.

<a id="tests"></a>
## Tests (P15)

- **Per target framework:** tests run on each target, net48 included where the library supports it (Windows runs it natively; deep_tools reports a gap where it can't).
- **API tests:** the public surface tested through the public surface only, the way callers use it; a test project that uses `InternalsVisibleTo` for everything proves less.
- **Package tests:** the packed `.nupkg` restored into a fresh project and used, so missing files and wrong target folders show up. Package validation against the last release where the project has it.
- **Generators:** snapshot tests of the generated source, a test that a second identical run is cached (`trackIncrementalGeneratorSteps`), and tests of each diagnostic.
- **Protocol clients:** a fake server for rate limits, disconnects, resumes and malformed messages; no test talks to the real service.
