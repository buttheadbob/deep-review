# DeepRules

A Roslyn analyzer for the `deep-review` skill. It flags code shapes behind defects that hub reviewers found in Space Engineers 1 plugins and that the usual analyzer packs (NetAnalyzers, Meziantou, VS Threading, Roslynator, Sonar, IDisposableAnalyzers, AsyncFixer, ErrorProne.NET) do not report.

The gate counts every hit, and nothing reads the report but a parser, so each rule is one of two kinds:

- **Counted** (no custom tag): every hit is a real defect that has to be fixed. The rule decides only from facts the compilation gives it (its options, references, symbols and real overrides), never from a method's name or a guess about how the code is used.
- **Review-only** (custom tag `ReviewOnly` in the `DiagnosticDescriptor`): the rule finds code a reviewer must judge, because whether it is a defect depends on something the compilation does not state. Its hits stay in `tools-report.json` under `reviewOnly[]` as input for the stage-2 review, and the gate does not count them. The reason for each is in [Gate status and context](#gate-status-and-context).

- 39 rules, `DR001` to `DR039` (`DR033`, `DR034` and `DR035` are the review-only halves split from `DR015`, `DR010` and `DR001`; `DR036` is the review-only widening of `DR023`). All are `Warning`, category `DeepReview`, message format `{0}`; each message states the defect and the fix, with no prefix.
- `HelpLinkUri` is `checks/<file>.md#<anchor>`, relative to the skill folder. Where a check file has a section for the rule, the anchor is that section's GitHub-style heading anchor. `persistence.md#dr020`, `performance.md#dr025` and `correctness.md#dr029` to `#dr032` have no matching section yet, so the check files need `<a id="dr0NN"></a>` anchors for those.

The deployed copy is `tools/bin/analyzers/DeepRules.dll`. A host loads it like any analyzer: `AnalyzerFileReference`, `<Analyzer Include="...DeepRules.dll" />`, or `csc /analyzer:`. Generated code is skipped. Game, Torch and Harmony types are matched by full metadata name (or by name and namespace for `MyEntities`/`IMyEntities`), so those rules work when the real assemblies are referenced and do nothing when they are not.

Rules that look across a whole type (DR002, DR006, DR009, DR011, DR025, DR034, and the one-level callee checks in DR003/DR016) see only the declaration in the current file. For a `partial` type split over files, a `-=`, `Dispose` or `Remove` in another file is not seen; all of those rules except DR009 are review-only, and DR009 counts only private timer members, which a `partial` type can still dispose in another part (the one gap left). DR012 and DR013 look for the matching `-=` or `Unpatch*` anywhere in the compilation (syntax only), so a removal in another type or file silences them.

## Context

Two helpers, both built once per compilation in a `RegisterCompilationStartAction`, so a rule that does not apply registers nothing and costs nothing per node.

**`HostContext`** reads the compilation's referenced assembly names (case-insensitive):

| Flag | Assembly names | Used by |
|---|---|---|
| Game | starts with `Sandbox.`, `VRage` or `SpaceEngineers.`, or is `HavokWrapper` | DR032 (MyEntities exists only in the game), DR031 message wording |
| Harmony | starts with `0Harmony`, `Harmony` or `Lib.Harmony` | DR013 and DR031's AccessTools part (that API exists only in Harmony), DR015/DR033 Harmony patches |
| Plugin host | `Torch` or `Torch.*` (Torch, Torch.API, Torch.Server), `Magnetar` or `Magnetar.*` (Magnetar.Protocol), starts with `Quasar.Plugin` (Quasar.Plugin.Abstractions) | game/plugin mode of DR010/DR034 |
| Game or plugin | any of the three | which static-state check runs (DR010 outside, DR034 inside), and whether DR029/DR030 messages mention the hub loaders |

Left out on purpose: `Pulsar` (every Pulsar client plugin references the game's own assemblies, which already count, and `Pulsar.Client` is the unrelated Apache Pulsar client), `Steamworks` (every Space Engineers plugin references VRage, and Steamworks.NET is used by many other games), and a bare `Torch` prefix (it would match TorchSharp). `tests/DeepRules.Tests/ContextTests.cs` checks every name above, and that TorchSharp, MagnetarSoft, Pulsar.Client, Steamworks.NET and Newtonsoft.Json do not count.

**`HostApi`** resolves the game's and Torch's real callback types with `GetTypeByMetadataName`. A method is a *game callback* only if it overrides or implements a member they declare, and runs *every frame* only if that member is one the game calls every frame; a Harmony patch is per frame when its `[HarmonyPatch(typeof(T), "Name")]` target resolves to such a method. Names alone never count, in any compilation (`UpdateMessageAsync`, a plain `public void Update()`).

| Type | Callbacks | Every frame |
|---|---|---|
| `VRage.Plugins.IPlugin` (and its `IDisposable.Dispose`) | all members | `Update` |
| `VRage.Plugins.IHandleInputPlugin` | all members | `HandleInput` |
| `Torch.API.Plugins.ITorchPlugin`, `Torch.TorchPluginBase` | all members | `Update` |
| `VRage.Game.Components.MySessionComponentBase` | all members | `UpdateBeforeSimulation`, `UpdateAfterSimulation`, `Simulate`, `Draw`, `HandleInput` |
| `VRage.Game.Components.MyGameLogicComponent`, `VRage.Game.Entity.EntityComponents.Interfaces.IMyGameLogicComponent` | all members | `UpdateBeforeSimulation`, `UpdateAfterSimulation` |
| `VRage.Game.Entity.MyEntity` | `Update*` members | `UpdateBeforeSimulation`, `UpdateAfterSimulation` |

The `*10`/`*100` updates, `UpdateOnceBeforeFrame` and `UpdatingStopped` are callbacks but not every frame.

**Per frame by reachability** (DR023, DR024): a method also runs every frame when an every-frame override or patch reaches it through direct calls in this compilation: invocations and constructor calls that bind to a method with source, made on the caller's unconditional path (the same test DR023 uses for work: not behind a branch, a loop body, a catch, `&&`/`||`/`??`/`?.`, a nested function or an earlier `return`/`throw`). Delegates, method groups, lambdas, virtual dispatch to other implementations and reflection are not followed. The graph is built per method and resolved breadth first in a compilation-end action, and the message names the chain (`Plugin.Update (overrides IPlugin.Update) → Session.Update → Commands.Tick`). DR033 is unaffected: it is about the callbacks themselves, not about what runs every frame.

**Periodic by any path** (DR036, review-only): the same graph, widened where DR023 cannot prove the work runs every time. Roots are the every-frame overrides and patches above, plus timer callbacks the compilation shows: a handler added to `System.Timers.Timer.Elapsed` (a method group, or a lambda as its own root) and the callback passed to a `System.Threading.Timer`. From them it follows every call wherever it is (conditional calls, loop bodies, lambda bodies, method groups passed as arguments) and virtual or abstract calls into every override in this compilation. It reports LINQ, allocations, capturing closures, reflection and file calls anywhere in the reached methods and lambdas, except work DR023 already reports. A reviewer decides whether the path runs in steady state; guards such as `if (++_tick % 60 != 0) return;` throttle on purpose. Found after Sens Essentials' sim speed timer (`Timer.Elapsed` → game invoke lambda → abstract `Tick` override) built a LINQ list every second that neither DR023 nor the allocation filter reported.

**Token flow** (DR001, in `TokenFlow.cs`): a `CancellationTokenSource.Cancel()` under a lock, on a source held in a field of the type (directly, by element, by `foreach`, or through a local taken from it), is DR001 only when that field's token provably reaches code that `Cancel()` runs on the calling thread by contract: `CancellationToken.Register`/`UnsafeRegister`, `CancellationTokenSource.CreateLinkedTokenSource` (followed to the linked source's `.Token`), or `Task.Delay(..., token)` awaited with `ConfigureAwait(false)`. The token is followed through the field's `.Token` reads, a local stored into the field before the read (`_runs.Add(cts)` then `cts.Token`), locals, and arguments into parameters of methods in this compilation, to any depth (resolved at compilation end). Everything else under a lock (other triggers, a polled token, a plain `await`, which may resume on a captured context) is DR035, review-only.

**The compilation's options** decide DR030 (`NullableContextOptions` `Disable` or `Warnings`, the annotation context off) and DR012 (`OutputKind`: libraries only). DR029 reads the tree's `PreprocessorSymbolNames` to say whether the compilation defines the symbol.

## DR039, the WebSocket handshake

One call is accepted, and only at that call: `SHA1.HashData(x)` (`byte[]` or `ReadOnlySpan<byte>`), or `SHA1.Create()` followed by `ComputeHash(x)` (a local that only calls `ComputeHash(byte[])` and `Dispose()`, or `SHA1.Create().ComputeHash(x)`), where all three hold. Each is read from the code of the method; nothing is guessed from names except the one parameter case below.

1. **What is hashed.** `x` is `Encoding.UTF8.GetBytes(t)` or `Encoding.ASCII.GetBytes(t)` (a local set once and never changed may stand for it), or `Encoding.X.GetBytes(key).Concat(Encoding.X.GetBytes(guid)).ToArray()`. `t` is exactly two parts and nothing else: `key + guid`, `$"{key}{guid}"` (no format or alignment), or `string.Concat(key, guid)` (a local set once may stand for the text). `guid` is constant text equal to `258EAFA5-E914-47DA-95CA-C5AB0DC85B11`, compared exactly (the literal, a `const`, or a `static readonly string` field with that initializer that nothing assigns again; a changed digit or letter case is a hit). `key` is the value of a header named `Sec-WebSocket-Key`: an indexer `h["Sec-WebSocket-Key"]`, `h.Get("Sec-WebSocket-Key")` or `h.TryGetValue("Sec-WebSocket-Key", out var key)` on any receiver (the name is constant text, compared without case as header names are, so `Request.Headers`, a `NameValueCollection` or a dictionary of parsed lines all work), the first group of `Regex.Match(text, "...Sec-WebSocket-Key...").Groups[n].Value`, a local set once from one of these, or a `string` parameter named `secWebSocketKey` or `webSocketKey` (compared without case, `_` and `-`). That last case is a name, so the rule cannot see the caller: it is accepted because the other two conditions still bind, and a reviewer reads the caller. `.Trim()` and `.ToString()` may follow the key. A byte array assembled with `Buffer.BlockCopy` or `Array.Copy`, `string.Format`, a key from any other source or header, and `Encoding.Unicode` are not accepted.
2. **What happens to the digest.** It only goes (directly or through a local set once) to `Convert.ToBase64String(digest)` (the `byte[]` or `ReadOnlySpan<byte>` overload with no options). Hex, comparison, storing it and any other use are hits.
3. **Where the Base64 text goes.** Only into the `Sec-WebSocket-Accept` header value: `response.Headers["Sec-WebSocket-Accept"] = text`, or `Add`, `Append`, `Set`, `TryAdd`, `AddHeader`, `SetHeader` or `AppendHeader` with that constant name and `text` as the value; or into the `Sec-WebSocket-Accept` line of the 101 response, where the constant text before it ends a line `Sec-WebSocket-Accept:` (a space may follow; the line starts the string or follows a line feed), the whole string (or an interpolated string) is turned into bytes with `Encoding.UTF8` or `Encoding.ASCII`, and those bytes are written with `Write`, `WriteAsync`, `Send` or `SendAsync` on a `NetworkStream`, `SslStream` or `Socket`. A file, a log, a `FileStream`, a `StreamWriter` (its destination cannot be shown), another header, a return from a public or internal method or a lambda, and a comparison are hits. `text` may be returned from a **private** method returning `string`: the rule then reads every call of that method in the type (all parts of a partial type) and each must use the result as above; a method group, no caller or one bad caller is a hit.

The rest of the pattern is as strict: the `SHA1` object is held only in a local, never assigned again, never passed on or stored in a field, and a `SHA1Managed` or `SHA1CryptoServiceProvider` is never accepted. A call that looks like the handshake but fails any condition is reported at the call with the first condition that fails.

**CA5350, S4790 and SCS0006** (the three analyzer rules that also report SHA-1) stay on, unchanged, in `deep.globalconfig`. `HandshakeSuppressor` (a `DiagnosticSuppressor` in `DeepRules.dll`, suppression ids `DR039A`, `DR039B`, `DR039C`) drops each of them only when its location is exactly the accepted call, or the `SHA1.Create` / `SHA1.HashData` part of it, and the call passes the same check DR039 uses. The analyzer and the suppressor call one function, `Handshake.Evaluate`, so they cannot disagree. A dropped result is a suppressed diagnostic in the gate record (`suppressedDiagnostics[]`), not a gate issue and not hidden. RS0030 no longer reports SHA1, because the `T:` ban was replaced by this rule. Tests: `tests/DeepRules.Tests/HandshakeTests.cs`.

`global.json` pins the .NET 10 SDK (10.0.403, rolling forward within 10.0.x).

### Layout

- `src/DeepRules`: the analyzer. `Rules.cs` holds the descriptors (and the `ReviewOnly` tag), `Util.cs` the shared helpers (symbol names, lock regions, continuation triggers, "unknown code", per-frame and logging checks), `HostContext.cs` the reference-based context, `HostApi.cs` the game's and Torch's real callback members, `TokenFlow.cs` DR001's token-flow proof, and one analyzer class per check file.
- `tests/DeepRules.Tests`: xUnit tests on a hand-rolled harness (`Harness.cs`). `Stubs.cs` holds game, Harmony and Torch stand-ins with the real full names; the harness compiles each set into its own assembly named like the real one (`Sandbox.Game`, `0Harmony`, `Torch.API`) and references the ones a test asks for (`Host.None`, `Game`, `Harmony`, `Torch`; the default is `Game | Harmony`). Each snippet is compiled with `CSharpCompilation` against the .NET 10 reference set (the test host's shared framework) **and** the .NET Framework 4.8 reference assemblies, with no preprocessor symbols, nullable enabled unless the test sets another `NullableContextOptions`, as a library unless it sets another `OutputKind`, then run through `CompilationWithAnalyzers` on Roslyn 4.14. A snippet that does not compile, or an analyzer exception, fails the test. `Fires`/`Silent` assert the same result on both reference sets (the APBL converter test is .NET 10 only: `System.Text.Json` is not in net48). `AnalyzeReferencing` compiles against empty assemblies of chosen names (`ContextTests.cs`). Every context-limited rule has a test that is silent without its reference or setting and one that fires with it.
- `tests/LoadSmoke`: a project that loads DeepRules as an analyzer in the SDK compiler; not part of the solution.
